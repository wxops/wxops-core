# Release Notes

## Highlights

v0.4.0 is the **Phase 0 API freeze** release: every XRD now exposes a
consistent `status.created`/`status.ready` contract, `XTenantApp` gains real
Prometheus monitoring, and the repository ships an offline test suite plus
dual-forge CI ahead of going public.

**Status parity** is the headline change. Before this release, only
`XTenantApp` exposed reliable readiness — a portal creating a Gitea repository
or a database cluster had no supported way to learn whether it worked. All
seven packages now expose `created` and `ready`, derived from observed
composed-resource state rather than Crossplane's native `type: Ready`
condition, which remains unreliable on Crossplane v2.3 with function-kcl
v0.12.1. See [`docs/status-contract.md`](../docs/status-contract.md) for the
full per-package field reference.

**`XTenantApp` monitoring** moves from pod annotations that silently did
nothing to a real `ServiceMonitor`/`PodMonitor` emission via
`spec.parameters.monitoring`. This requires a one-time cluster change — see
Upgrade notes.

Also in this release: `darlane.rbac` is permanently dropped from core (RBAC
belongs in the GitOps repo, not a composition — see Decided and rejected in
`ROADMAP.md`), `targetCluster` is threaded through every KCL package ahead of
multi-cluster work, and the project gained an offline test suite, a licence,
a contributing guide, and CI on both Gitea and GitHub.

### Status parity across all seven XRDs

| Package | Before | Now |
|---|---|---|
| `tenant-app` | `created`, `ready` | unchanged (already had it) |
| `tenant-database` | no readiness fields | `created`, `ready` — derived via `_isReady()` over `ocds`, same pattern as `tenant-app` |
| `platform-database-clusters` | no readiness fields | `created`, `ready` — same pattern |
| `gitea-user` / `gitea-org` / `gitea-team` / `gitea-repository` | no status schema at all | `created`, `ready`, plus per-resource identifiers (`userId`, `orgId`, `teamId`, `repoId`, clone URLs) |

The four `gitea-*` packages take a different implementation path than the
three KCL-based ones: `ToCompositeFieldPath` patches read
`status.atProvider.outputs` off the underlying Terraform `Workspace`, since
those outputs only exist after a successful `terraform apply`. **One resulting
difference worth knowing:** on the `gitea-*` packages, `created`/`ready` are
**absent** — not `false` — until the first successful apply, because the patch
itself doesn't run until its source path exists. The three KCL packages always
emit an explicit boolean. Treat "absent" the same as `false` when polling.

`initial_password` on `gitea-user` remains routed to the connection secret and
is never exposed in status.

### `tenant-app` readiness — split, not widened

`status.ready` previously covered the Deployment, Service, and Ingress only,
excluding the cert-manager `Certificate`. Rather than widen `ready` to include
everything, this release **splits** it:

```yaml
status:
  ready:             true    # core workload only
  dependenciesReady: false   # e.g. Certificate not yet issued
```

This lets a consumer render "app is up, TLS still issuing" honestly instead of
a blanket "not ready." `XTenantApp` does not compose an `XTenantDatabase` —
`secretsFrom.database` only wires an existing Secret in by name — so database
readiness was never in scope for either field and still isn't.

### Darlane status

The debug-twin lane now reports real state, present only when
`darlane.enabled: true`:

```yaml
status:
  darlane:
    ready:              true
    replicas:           1          # observed, not desired
    trafficMode:        weighted   # none | weighted | header | both
    ttl:                "4h"       # the configured duration, echoed as-is —
                                    # not an expiry timestamp
    serviceAccountName: payment-api-darlane
```

### `darlane.rbac` — dropped, not deferred

The XRD description previously advertised "scoped RBAC for developer access,"
but no `Role` or `RoleBinding` was ever implemented. That promise is now
**permanently removed**, not scheduled — compositions in this repo do not
emit Kubernetes RBAC, and `providers/rbac-provider-kubernetes.yaml` is
deliberately not granted `rbac.authorization.k8s.io`. Granting it would make
provider-kubernetes a privilege-escalation vector, and `pods/exec` cannot be
name-restricted by RBAC regardless of who authors it, so the original design
was never as scoped as it read.

The seam that replaces it: the composition creates the Darlane
`ServiceAccount` and now publishes its name at
`status.darlane.serviceAccountName`; a `Role`/`RoleBinding` binding to that
name is authored in the GitOps repo, where it gets human review on a diff.

### Observability — `ServiceMonitor` and `PodMonitor`

`XTenantApp` expressed monitoring as `prometheus.io/*` pod annotations, which
did nothing on this platform — no scrape job ever read them.
`spec.parameters.monitoring` replaces that with a real Prometheus Operator
CRD:

```yaml
monitoring:
  enabled: true
  kind: auto          # auto | ServiceMonitor | PodMonitor
  port: 9090            # defaults to containerPort when unset
  path: /metrics
  interval: 30s
  scrapeTimeout: 10s
  sampleLimit: 5000
  honorLabels: false
  metricRelabelings: []
```

`auto` resolves to `ServiceMonitor` when `service.enabled: true`, `PodMonitor`
otherwise — the only option for Service-less workloads, and the one that keeps
scraping a pod through a readiness failure, which a `ServiceMonitor` cannot.
Setting `kind: ServiceMonitor` explicitly without a Service now fails loudly at
render time rather than emitting nothing.

The generated Service port is **not yet named** — the emitted monitor targets
`targetPort` instead, the zero-risk option that leaves the live Service
untouched. Naming the port is tracked as a follow-up.

Full design: [`docs/observability.md`](../docs/observability.md).

### `targetCluster` — threaded, not yet active

All three KCL packages (`tenant-app`, `tenant-database`,
`platform-database-clusters`) now read `spec.parameters.cluster` and route
every composed `Object` through the named `ProviderConfig` instead of a
hardcoded `"default"` — 29 sites in total. Behaviour-neutral today: nothing
consumes this yet, since no spoke `ProviderConfig` exists. This unblocks the
multi-cluster work in [`docs/multi-cluster.md`](../docs/multi-cluster.md)
without a later rewrite of every composition.

### API version — staying on `v1alpha1`

All seven XRDs continue to serve `v1alpha1` only. Every change in this release
is additive, so nothing forced a bump; promoting to `v1beta1` is deferred to
the Phase 4 OSS release, the natural point to make a stability commitment.
Recorded as a decision in `VERSIONS.yaml`, not an oversight.

### Testing and CI

- An offline test suite (`tests/`) — no cluster required. Golden render tests
  (19 cases), cross-cutting invariants and third-party field contracts (18
  rules), and strict XRD conformance including 9 negative cases that must be
  rejected. `make test` is the merge gate; see
  [`tests/README.md`](../tests/README.md).
- `pr-validate.yaml` on both Gitea and GitHub — lint, schema, package build,
  the full test suite, and release hygiene checks on every pull request.
- A local `no-commit-to-branch` safety net blocks accidental direct commits to
  `main` for anyone with pre-commit hooks installed.

### Project infrastructure

- **`LICENSE`** (Apache-2.0) and **`NOTICE`** added.
- **`CONTRIBUTING.md`** — setup, the change loop, and the full checklist for
  adding a new package, including the test cases it owes.
- Issue templates for bug reports, feature requests, and questions.
- **`package/install/*.yaml`** repointed from the private Gitea registry to
  `ghcr.io/wxops` — the previous host was unreachable by anyone outside the
  platform team.
- **`docs/status-contract.md`** — a single-page reference of every package's
  `status` fields, written for portal integration.

## Upgrade notes

**Required: provider RBAC for monitoring.** Apply the updated
`providers/rbac-provider-kubernetes.yaml` before using
`spec.parameters.monitoring` on any `XTenantApp`:

```bash
kubectl apply -f providers/rbac-provider-kubernetes.yaml
```

Without this, every emitted `ServiceMonitor`/`PodMonitor` fails `forbidden` at
reconcile with no other signal. Safe to apply proactively even if you don't
use monitoring yet.

**No action required for status parity, the readiness split, or Darlane
status** — all additive fields, nothing removed or renamed.

**`darlane.rbac` was never functional**, despite `release-notes/v0.3.0.md`
stating it "emits a scoped `Role`/`RoleBinding`" — that was incorrect; no such
block ever existed in `package/tenant-app/xrd.yaml` or `kcl/tenant-app/main.k`.
The correction is recorded in `ROADMAP.md`. If you were relying on it existing,
nothing changes for you, because it never worked; author the
`Role`/`RoleBinding` in your GitOps repo against
`status.darlane.serviceAccountName` instead.

**Portal integrations should read
[`docs/status-contract.md`](../docs/status-contract.md)** before binding to
any package's `status` — in particular the absent-vs-`false` distinction on
the `gitea-*` packages, and the `ready`/`dependenciesReady` split on
`tenant-app`.
